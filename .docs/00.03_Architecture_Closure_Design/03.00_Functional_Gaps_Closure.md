# 3. Closing Functional Gaps Remaining from Contract Classification

The previous ten observations address the consistency of boundaries and artifacts; however, there are fundamental functional gaps that cannot be considered resolved simply by addressing those points.

Here are the proposed solutions:

## G-01 — Stage Callable Contract

The solution lies in the generic contract described in F-08.

However, a clear distinction must be made between:

- Stage Definition.
- Stage Entity.
- Stage Invocation.
- Stage Execution Context.
- Stage Execution Result.
- Stage Operational State.

Each concept serves an independent function.

## G-02 — Stage Flow Result Strategy

The solution is a "Generic Stage Result Envelope" containing a "Specialized Payload," rather than a "Universal FlowResult."

## G-03 — Generic Pipeline Root Contract

I disagree with the idea of ​​creating a "Root Entity" solely because a "Pipeline Root" exists within the operational model.

Options:

| Option | Description |
|---|---|
| A | Create a Generic Pipeline Root Entity | Introduces an unproven concept |
| B | Leave the Root entirely to the consumer | High flexibility, but lacks a GPWCF contract for Root integration |
| C | Define a Pipeline Invocation Contract without a Root Entity | Decouples the invocation from the ownership of a Root entity |

My recommendation: C

In this approach, the GPWCF does not possess a "Generic Root Entity." Instead, it can define an optional contract that describes:

- Pipeline Invocation Identity.
- Stage Invocation Requests.
- Shared Pipeline Context.
- Stage Result Collection.
- Overall Pipeline Settlement.
- Correlation Information.

The "Pipeline Root Flow" itself remains consumer-owned and is executed by Prefect.

This allows us to achieve Pipeline Root integration without imposing a "Root Entity" on all consumers. ## G-04 — Error Model Dependency Closure

The solution involves a constrained "Generic Diagnostics Contract," followed by the decoupling of the "Generator Error Model."

A "Dependency Closure Analysis" must be performed for all contracts that utilize the Error Model. This will identify which contracts:

- Truly require "Generic Diagnostics."
- Require specialized error-handling contracts.
- Require generator-specific error semantics.
- Require none of the above.

## G-05 — StepExecutionResult Optional Result Slots

This is a critical point.

If we include mandatory fields for every "Supporting Pattern" within `StepExecutionResult`, every user of the Core will become dependent on all these patterns.

Options:

1. Fixed fields for every pattern.
2. A general dictionary for results.
3. Typed extension slots.
4. Result composition using typed contributions.

My recommendation: A combination of 3 and 4.

Conceptual structure:

```
StepExecutionResult
├── Core Result
├── SPU Results
├── Optional Result Contributions
└── Settlement Information
```

The "Core Result" remains mandatory, while optional results are added via "Typed Contributions" that possess clear identities and types.

Unconstrained dictionaries or the use of `Any` as a primary solution must be avoided.

Ideally, there should be an "Extension Registry" mechanism local to the result or the "Step Definition," rather than a global runtime registry.

For example:

```
StepExecutionResult[TCoreResult, TOptionalContributions]
```

However, this is merely a design direction; we must evaluate its impact on type complexity, API consumption, and the feasibility of serializing results across processes.

## G-06 — Single Step Publication Specialization

This is a responsibility that should not be generalized across all steps.

I propose:

- Keeping "Publication" confined to error handling or specialized capabilities—but only if it is proven that its semantics are indeed part of error handling. - Decouple "Publication Operation" from "Publication Policy."
- Decouple "Reservation" from "Commit."
- Define outcomes—Confirmed, Failed, Unknown, or Conflict—based on actual requirements.
- Assign "Recovery" and "Retry Policy" responsibilities to the consumer or a specialized capability, rather than to the generic "Step."

This ensures that a "Step" does not evolve into a general-purpose "Transaction Manager."

## G-07 — Production Prefect Functional Binding

There must be a test verifying that the Prefect integration invokes actual GPWCF contracts, rather than relying solely on "fixture" workflows.

Required tests include:

- Stage Deployment Binding.
- Step Subflow Binding.
- SPU Task Binding.
- Supporting Unit Binding.
- Domain Result Mapping.
- Operational State Mapping.
- Identity Correlation.
- Context Propagation.
- Failure and Cancellation Mapping.

Furthermore, this testing must be decoupled from the testing of the Prefect framework itself.

The successful execution of a flow by Prefect does not, in itself, validate the success of the GPWCF integration.

# 7. PHASE-03 disposition and remaining contract gates (2026-11-09)

The accepted PHASE-03 artifacts refine the proposals above into the following implementation constraints. The proposal text in this document is not, by itself, an approved runtime contract.

- **G-01 Stage Callable:** remains unresolved. No callable signature, Stage invocation module or Prefect Stage binding implementation is materialized until the dedicated contract is approved.
- **G-02 Stage Flow Result:** the generic envelope/specialized-payload approach remains a candidate, not an approved universal StageResult schema. Stage owns its specialized Flow Result; no Core stage/results package is materialized.
- **G-03 Pipeline Root:** no Generic Pipeline Root Entity is introduced. The consumer and external workflow runtime retain Root Flow ownership. Any optional Pipeline Invocation Contract requires its own contract decision.
- **G-04 Error Model:** Generator Common Error Model remains consumer-owned. Generic diagnostics and conditional Step Error Model require explicit dependency-closure and contract approval.
- **G-05 Optional Result Slots:** typed contributions remain a design direction; final typing, extension and serialization semantics are not implemented by the filesystem skeleton.
- **G-06 Single Step Publication:** publication/recovery policy remains a concrete consumer specialization; no generic transaction manager or universal publication policy is introduced.
- **G-07 Production Prefect Binding:** fixture qualification is not production binding evidence. Real GPWCF contract binding and failure/cancellation/recovery qualification remain required.

PHASE-03 also resolves the initial distribution shape as one GPWCF distribution with a dependency-free Core base and optional Prefect extra. The Python build backend and build-system dependency pinning remain a separate release gate.

The solution dependency locations are:
- External dependency/source assets: SMRB solution-root .dependencies/.
- Shared developer Python virtual environment: SMRB solution-root .env/.

The initial filesystem authorization covers directories and minimal package markers only. It does not authorize placeholder implementations, speculative public exports, or edits to specialized Primary Architecture contracts.
