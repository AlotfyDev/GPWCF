# 09 — Maintenance, Update and Recovery Runbook

## 1. Objective

Define a safe repeatable procedure for maintaining Prefect and its dependency bundle without silently changing the package contract or affecting other SMRB projects.

## 2. Trigger conditions

Review the bundle when:
- Prefect 3.9.2 receives a candidate update;
- a security advisory affects a locked distribution;
- CPython version, architecture or target OS changes;
- a transitive package drops or adds a compatible wheel;
- a build backend or test runner version changes;
- an integration test reveals runtime/API behavior changes.

Do not update dependencies merely because a newer version exists. First assess compatibility with the accepted GPWCF integration design and current target runtime.

## 3. Update workflow

1. Record the proposed Prefect version and reason for change.
2. Review the accepted adoption decision and release-gate requirements.
3. Resolve the candidate closure in a clean CPython 3.15.1 Windows x64 environment.
4. Generate a resolver report; do not freeze an unrelated developer environment.
5. Review every package addition/removal/version change and platform marker.
6. Review licenses and security advisories.
7. Acquire wheel artifacts for the exact target.
8. Build any necessary source-only artifact in a controlled temporary build environment; retain source and built wheel provenance.
9. Generate hash-locked requirements and update the manifest.
10. Run Verify-GpwcfBundle.ps1.
11. Create a fresh temporary environment and install offline.
12. Run pip check, Core-only tests without Prefect, Prefect integration tests and E2E tests.
13. Build and install the GPWCF wheel; inspect its METADATA.
14. Review changes to the architecture binding and operational mapping if Prefect semantics changed.
15. Obtain release-gate/license sign-off before shipping.

## 4. Do not mutate in place without a recovery point

Before changing locks or artifacts:
- preserve the current manifest and lock files in version control or an approved immutable record;
- record hashes of the prior bundle;
- use a separate candidate directory or branch for resolution;
- do not overwrite the currently qualified wheelhouse until the candidate passes all gates.

The current bundle is a verified local dependency set; this does not imply it is a backup or an approved release repository.

## 5. Environment replacement

Do not replace the current .env in place. Create a new environment path with New-GpwcfEnvironment.ps1, verify it, and explicitly switch the project interpreter only after acceptance.

If a new environment fails provisioning, preserve it for diagnosis. Do not delete it automatically before collecting pip output and the target runtime identity.

## 6. Rollback

If a candidate update fails:
1. stop using the candidate environment;
2. retain logs and the failed candidate manifest;
3. restore the previously approved lock/manifest/artifact set from the preserved revision;
4. create a fresh environment from the known-good runtime and lock;
5. reinstall offline and verify hashes;
6. run pip check and the relevant test suites;
7. document the cause and the rollback evidence.

Do not downgrade packages inside an unknown partially mutated environment and then assume it is equivalent to a clean reconstruction.

## 7. Operational commands

Verify bundle:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File <bundle>\scripts\Verify-GpwcfBundle.ps1

Install Prefect profile:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File <bundle>\scripts\Install-GpwcfDependencies.ps1 -TargetPython <environment>\Scripts\python.exe -Profile prefect

Install development profile:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File <bundle>\scripts\Install-GpwcfDependencies.ps1 -TargetPython <environment>\Scripts\python.exe -Profile development

Health check:
<environment>\Scripts\python.exe -m pip check

Version check:
<environment>\Scripts\python.exe -c "import sys,prefect; print(sys.version); print(prefect.__version__)"

## 8. Lessons

- Reproducibility requires both a lock and the exact compatible artifacts.
- An environment is disposable; the lock, manifest, source provenance and verification report are the durable record.
- Keep candidate and qualified bundles separate until review completes.
- Rebuild environments rather than editing their base interpreter metadata.
- Preserve Core-only verification after every Prefect update.
