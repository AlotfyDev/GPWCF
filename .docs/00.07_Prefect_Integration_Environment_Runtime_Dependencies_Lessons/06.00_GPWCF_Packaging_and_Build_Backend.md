# 06 — GPWCF Packaging and Build Backend

## 1. Objective

Record the package metadata repair, the build backend boundary, the offline wheel build method, and the verification that the Prefect extra remains optional.

## 2. Build metadata

The package uses PEP 621 project metadata and PEP 517/518 build configuration.

Relevant current declarations:
- distribution: gpwcf;
- version: 0.1.0;
- Python range: >=3.15,<3.16;
- base project dependencies: empty;
- optional prefect extra: prefect==3.9.2;
- build backend: setuptools.build_meta;
- build-system requirement: setuptools==84.2.1;
- package source root: src;
- package data includes gpwcf/py.typed.

## 3. Packaging defect and correction

The original pyproject.toml incorrectly represented include-package-data as a TOML table:

[tool.setuptools.include-package-data]
true = true

Setuptools expects a Boolean setting under [tool.setuptools]. It was corrected to:

[tool.setuptools]
package-dir = {"" = "src"}
include-package-data = true

The correction was followed by a successful offline wheel build.

## 4. Why build isolation matters

setuptools is a build-system dependency. It must be available to the build backend, but it must not become a GPWCF runtime dependency.

The bundle retains setuptools 84.2.1 in build-backend.lock and in the wheelhouse. The build verification used a temporary venv with that exact local wheel.

## 5. Reproduced build method

The successful qualification used the following pattern:

1. Create a temporary CPython 3.15.1 virtual environment.
2. Install setuptools 84.2.1 from the local wheelhouse with no index.
3. Build with pip wheel --no-deps --no-build-isolation.
4. Inspect the produced wheel metadata.
5. Install the wheel into a separate clean temporary environment without Prefect.
6. Import Core package entry points and confirm Prefect is absent.
7. Remove temporary build/test environments and temporary wheel output.

No network resolution was required for the build backend.

## 6. Wheel metadata acceptance

The produced wheel metadata was inspected. Observed:
- no base Requires-Dist entries;
- Prefect 3.9.2 appears only under the Prefect optional extra.

The wheel was installed in a clean temporary environment. Imports of gpwcf, gpwcf.core and gpwcf.public_api.core succeeded while importlib confirmed Prefect was not installed.

This is stronger evidence than merely parsing pyproject.toml because it validates the generated distribution metadata and a real installed-wheel Core import.

## 7. Generated build outputs

The temporary build output and generated build metadata directories were removed after verification. No wheel artifact is claimed to have been retained as a project release output. The bundle retains dependency artifacts, not a signed GPWCF release wheel.

## 8. Lessons

- TOML nesting is semantically significant; a valid TOML document may still express an invalid setuptools configuration.
- Keep build dependencies separate from runtime dependencies.
- Inspect the built wheel METADATA rather than relying solely on source metadata.
- Test the installed wheel without Prefect to prove the Core boundary survives packaging.
- A successful wheel build is not equivalent to release approval or a completed license audit.
