# 01 — Environment Scope and Architecture Boundaries

## 1. Objective

Define which parts of the GPWCF/Prefect setup own the Python runtime, third-party packages, build tooling, and orchestration behavior. This boundary is the first control against accidental Prefect coupling in Core or dependency leakage between SMRB projects.

## 2. Responsibility split

| Concern | Owner | Rule |
|---|---|---|
| GPWCF domain contracts and Core behavior | GPWCF Core | Must remain importable without Prefect |
| Prefect Flow/Task/Deployment bindings | GPWCF Prefect integration | Prefect-specific imports and runtime interaction stay in integration modules |
| Pipeline topology and root orchestration | Consumer | GPWCF does not become a universal pipeline orchestrator |
| Python interpreter/runtime | Host/solution runtime provisioning | The GPWCF package does not bundle or own an interpreter |
| Prefect runtime dependency | Optional GPWCF extra and solution dependency bundle | Opt-in; exact version pinned |
| Test runner | Development/test profile | Not a base runtime dependency |
| Build backend | PEP 517 build-system | Build-time only; not a Core or Prefect runtime dependency |
| Local venv | Explicit environment owner | Installer acts only on the Python executable passed to it |

## 3. Dependency planes

### 3.1 Core runtime plane

Current package metadata declares an empty base dependency list. Core is designed to use the Python standard library and its own package modules only. Installing GPWCF Core must not pull Prefect.

### 3.2 Optional Prefect integration plane

The package declares Prefect 3.9.2 only under the optional dependency group named prefect. Consumers that require the integration opt in to that extra. A consumer that installs Core only must not need Prefect installed.

### 3.3 Test/development plane

pytest 9.2.0 is installed through the dependency bundle's test profile. It is not declared as a Core runtime dependency and is not required to import Core.

### 3.4 Build plane

setuptools 84.2.1 is declared under build-system.requires. It is needed to build the distribution and must not appear as a GPWCF base runtime dependency merely because it is used by packaging.

## 4. Physical locations and isolation

The bundle is located under the SMRB solution-root .dependencies directory. Its project-scoped subfolder is dedicated to GPWCF Python dependency artifacts. It reuses the existing solution shared CPython runtime stored under the PayloadDescriptionGenerator dependency folder.

The existing project environment is GPWCF\.env. The project .pyproj references this project-local environment. The bundle's installer does not search for or mutate arbitrary Python installations; it receives an explicit TargetPython.

Do not:
- add Prefect to GPWCF base dependencies or requirements intended for Core;
- import Prefect from Core modules;
- copy the private PayloadDescriptionGenerator dependency bundle into GPWCF;
- modify other SMRB project environments when provisioning GPWCF;
- treat the bundle's wheelhouse as portable to other Python ABIs, architectures, or operating systems.

## 5. Package metadata as verified

The current pyproject.toml declares:
- requires-python: >=3.15,<3.16;
- project.dependencies: empty;
- project.optional-dependencies.prefect: prefect==3.9.2;
- build-system.requires: setuptools==84.2.1;
- setuptools package discovery under src and package data for gpwcf/py.typed.

The include-package-data setting is a Boolean under [tool.setuptools]. Its earlier malformed TOML table form was corrected and the wheel build subsequently succeeded.

## 6. Boundary verification

The boundary was checked in two independent ways:
1. Architecture tests confirmed Core dependency/import constraints.
2. A clean temporary environment installed the built GPWCF wheel without Prefect, imported gpwcf, gpwcf.core and gpwcf.public_api.core, and confirmed Prefect was absent.

The wheel METADATA inspection showed no base Requires-Dist entries and Prefect only in the optional extra.

## 7. Lessons

- An optional dependency declaration is not sufficient on its own: Core imports must be exercised in an environment where Prefect is truly absent.
- A package build backend belongs to the build plane, not the runtime plane.
- A shared runtime location and a shared virtual environment are different concepts; do not conflate them.
- Dependency provisioning must be explicit about its target interpreter to avoid collateral changes.
