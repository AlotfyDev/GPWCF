# 08 — Prefect Runtime Integration and E2E Lessons

## 1. Objective

Record the Prefect runtime distinctions that affected the integration E2E tests and the repairs made to align test behavior with the actual Prefect 3.9.2 APIs and GPWCF domain result contracts.

## 2. Domain identity versus native runtime identity

The integration must preserve separate namespaces.

Domain-side identities include consumer pipeline invocation identity and GPWCF Stage, Step and SPU invocation identities. Prefect-side identities include Deployment ID, Flow Run ID, Task Run ID, Work Pool/Worker identity and native State.

A Prefect ID must never be cast to or reused as a GPWCF domain identity. One domain invocation can correlate with multiple Prefect native records, including wrapper Tasks and synthetic subflow/deployment invocation Tasks.

## 3. Parent identity recording

The E2E trace recorder required three distinct domain-level identity fields:
- stage_invocation_identity;
- step_invocation_identity;
- parent_domain_invocation_identity.

The Prefect native parent Flow Run ID is separate from the domain parent identity. The repaired _record() call sites now provide the parent domain identity and the native parent Flow Run identifier independently.

The tests assert the expected hierarchy at Pipeline Root, Stage, Step and SPU levels. This guards against treating Prefect's execution graph as the GPWCF domain graph.

## 4. Subflow return values are not Task futures

The original E2E code invoked Prefect subflows directly and then attempted to call .result() on their return values. A direct Flow/Subflow invocation returns its completed result directly; it does not behave like Task.submit() and does not return a Future with .result().

The test now stores the returned Step and Stage results directly. Collection variable names were also changed to reflect that these are completed results, not futures.

Do not apply Task.submit() assumptions to a direct Flow call.

## 5. Typed GPWCF result objects

The tests originally treated StepExecutionResult as a dictionary and accessed processing_artifact by string key. The Core contract returns a typed StepExecutionResult object. Its processing_artifact is represented by the Present result wrapper when a value is present.

The assertions now:
- verify the StepExecutionResult type;
- verify processing_artifact is a Present value;
- read the payload through the wrapper's value field;
- assert the expected normalized/measurement content.

This preserves the typed domain contract instead of weakening production code to satisfy an incorrect test assumption.

## 6. Prefect State name casing

The observed Prefect 3.9.2 completed state exposes State.name as Completed. The E2E assertion was aligned with that observed spelling rather than expecting COMPLETED. The state assertion remains an operational assertion only.

## 7. Domain result versus Prefect State

Prefect State describes native Flow/Task execution. GPWCF results describe domain processing. A native COMPLETED state does not automatically mean a domain success; a domain negative/partial result may be returned by a normally completed callable.

Likewise, a native FAILED/CANCELLED state does not by itself prove that no side effect occurred, that cancellation settled safely, or that previously accepted domain results should be revoked.

The integration must retain both the typed domain result and the native operational evidence independently.

## 8. Test outcome

After the _record() call-site and E2E assertion corrections:
- Prefect E2E: 3/3 passed.
- Prefect integration: 28/28 passed.
- Core architecture: 54/54 passed in a separate environment with Prefect absent.

## 9. Qualification limits

These tests qualify the exercised local fixture path. They do not establish universal Prefect cancellation, timeout, retry, worker-loss, durable recovery, multi-host or production deployment behavior. The detailed architecture binding and operational mapping documents retain their own qualification boundaries and draft status.

## 10. Lessons

- Test actual API return semantics, not assumed future semantics.
- Keep native execution metadata and domain invocation identities distinct.
- Test typed result contracts through their public types/wrappers.
- Never derive domain success or safe settlement from Prefect State alone.
- Add trace hierarchy assertions so future changes cannot silently collapse the two identity graphs.
